# mpp

The [mpp.dev](https://mpp.dev) documentation site and service directory for MPP, built with Vocs v2 and deployed on Vercel. Use this guidance when creating or updating MPP documentation.

## Commands

```bash
pnpm install --frozen-lockfile          # install (pnpm only)
pnpm check:ci                           # Biome format/lint (pnpm check fixes in place)
node scripts/generate-discovery.ts      # generate discovery output; CI runs it before typecheck and test
pnpm check:types                        # tsc --noEmit
pnpm test                               # vitest run (unit tests and scripts/*.test.ts)
pnpm check:markdown                     # audit generated Markdown output
pnpm check:generated                    # src/pages.gen.ts matches pnpm generate:pages
pnpm build                              # production build, type-checks every twoslash snippet; needs MPP_SECRET_KEY (CI uses a placeholder)
pnpm mcp-services:check                 # workers/mcp-services Worker
docker compose up -d --wait tempo && pnpm test:integration   # Tempo localnet integration tests
```

Run one test with `pnpm vitest run <path>`. `pnpm test:integration` (`integration/`) needs the Tempo localnet from `compose.yaml` (Docker). `pnpm test:e2e` (`e2e/`) covers the terminal demo. `pnpm check:services` probes live services over the network. `pnpm dev` runs the site locally; `.env.example` lists the variables live demos need.

  - Client: `src/pages/sdk/typescript/client/{Module}.{method}.mdx`

  - Core: `src/pages/sdk/typescript/{Module}.{method}.mdx`
- SDK index: `src/pages/sdk/index.mdx`. Python, Rust, Go and Ruby: `src/pages/sdk/{python,rust,go,ruby}/*.mdx`.
- `src/pages.gen.ts`: generated by `pnpm generate:pages`.
- `schemas/`: discovery and service directory schemas and data (`services.ts`, `mpp-proxy.json`, synced with `pnpm sync:mpp-proxy`).

## Conventions

- **Source of truth**: follow [paymentauth.org](https://paymentauth.org) (tempoxyz/mpp-specs) for protocol details (core scheme, methods, intents, HTTP and MCP transports) when documenting HTTP Payment auth parameters.
- **SDK references**: TypeScript is [wevm/mppx](https://github.com/wevm/mppx); the Ruby SDK is [stripe/mpp-rb](https://github.com/stripe/mpp-rb). Other SDKs are listed under MPP below.
- **Reference sites** for patterns and APIs: [Vocs](https://vocs.dev) (documentation framework: MDX, callouts, Cards), [Viem](https://viem.sh) (Ethereum library used in examples), [Wagmi](https://wagmi.sh) (React hooks, style reference), [Tempo](https://tempo.xyz) (Tempo blockchain and TIP-20 tokens).
- **mppx documentation sync**: when updating `mppx` interfaces, examples, reference pages, or the `mppx` dependency, review upstream `mppx/main` from the SHA in `.mppx-docs-sync`. After incorporating every relevant public change, update both `mppx_version` and `mppx_sha` in that bookmark to the reviewed upstream HEAD. Do not advance the bookmark before the docs are complete.
- **Python and Rust pages** keep the structure aligned with the existing indexes:
  - Lead with a short SDK overview and install steps
  - Include a quick-start client/server or core flow example
  - Use language-appropriate fences (`python`, `rust`)
  - Keep examples realistic and consistent with MPP terms (challenge, credential, receipt)
- **Generated Markdown**: follow [MARKDOWN.md](./MARKDOWN.md). Prefer component-local `markdown` exports; use `markdown.output.components` overrides for browser-only modules. Keep existing output plugins where page context is required. Add focused renderer tests and run `pnpm check:markdown`. Both builds and CI use `fail` mode.
- **Testing changes**: always make sure the site builds and types check: `pnpm check:types` must pass with no errors and `pnpm build` must complete. `pnpm test:e2e` must pass when changing the terminal demo (`src/components/Terminal.tsx`, `src/components/terminal-data.ts`, or related components).

### Rules

- **Alphabetize everything**: object properties in code examples and `###` parameter headings must be alphabetically ordered.
- **Install code-groups must include npm, pnpm, and bun**: every `:::code-group` with install commands must have all three tabs: `npm`, `pnpm`, and `bun`. Use `npm install`, `pnpm add`, and `bun add` respectively.
- **No `// @noErrors` in twoslash**: NEVER use `// @noErrors` in twoslash code blocks. All snippets must typecheck against the installed mppx types. If a snippet fails, fix the snippet or bump the mppx version; do not suppress the error.
- **Keep descriptions concise**: one line for the intro, brief explanations for parameters.
- **Show realistic examples**: use actual values that make sense.
- **Use `// @log:` comments**: show expected output inline.
- **Document all parameters**: mark optional ones with "(optional)".
- **Include type information**: always show the Type for each parameter.
- **Bash terminal blocks**: use ` ```bash [test.sh] ` with `$` prefixes for shell commands.
- **TypeScript twoslash**: use ` ```ts twoslash ` for TypeScript snippets that are expected to typecheck as valid, self-contained examples. Use bare ` ```ts ` for partial snippets, pseudo-code, package skeletons, illustrative fragments, or examples that depend on modules or symbols not installed in this repo.
- **Spec link Cards**: use the shared `<SpecCard to="..." />` component. Defaults to title `"IETF Specification"` and description `"Read the full specification"`. Override with `title` and `description` props when linking to a specific draft.
- **"IETF Specification"**: use "IETF Specification" (singular) when referring to the specifications collectively, not "Specs" or "Specifications".
- **Sequence diagrams**: use `<MermaidDiagram>` from `../../components/MermaidDiagram` for sequence diagrams and flow visualizations. Never use ASCII art diagrams. Follow the pattern: `<MermaidDiagram chart={\`sequenceDiagram ...\`} />`
- **Prefer configured handler references**: use configured handlers such as `mppx.tempo.charge` instead of string keys such as `'tempo/charge'` whenever possible.

### Tempo networks in examples

- Use the chain IDs under MPP below; never the retired one.
- Keep code examples within a single page on one Tempo network unless the section is explicitly comparing networks. For Sessions docs, default runnable examples to Tempo mainnet (`4217`, `tempo` from `viem/chains`, and `https://rpc.tempo.xyz`) and reserve Moderato (`42431`) for parameter descriptions, network reference tables, or pages that are specifically about testnet setup.
- When showing token or contract addresses in code examples, add a short inline comment naming the currency or contract whenever the name is not obvious from surrounding text:

```ts
currency: '0x20c0000000000000000000006a37DA5C996874BE', // OUSD on Tempo
```

## Be opinionated

When multiple approaches exist, recommend one as the default. Don't present options equally—pick the best path for most users and lead with it.

**Structure for pages with alternatives:**

1. **Lead with the recommended approach**—Show the single best option first, with a complete example
2. **Move alternatives to "Advanced options"**—Group other approaches under a secondary heading below the main content

**Examples:**

- Client SDK: Lead with `Fetch.polyfill`, move `Fetch.from` and `Mppx.create` to Advanced options
- Building with AI: Lead with `llms-full.txt`, move MCP/skills/markdown to Advanced options
- Installation: Show npm first in a code-group, not a table of choices
- Wallet-provider tabs: Put the generic or local wallet option first. Privy and other vendor-specific options always follow it.

If you're unsure which option to recommend, prefer:
- The approach with fewer steps
- The approach that modifies less existing code
- The approach labeled "Reference" or "Stable" over "Beta" or "Custom"

## Page structure

Every reference page follows this structure:

````mdx
# `{Module}.{method}`

Brief one-line description of what this function does.

## Usage

```ts twoslash [example.ts]
import { Module } from 'mppx'
// or 'mppx/client' or 'mppx/server'

const result = Module.method({
  param1: 'value1',
  param2: 'value2',
})

console.log(result)
// @log: Expected output
```

### With Custom Transport

Description of what this variant does and when to use it.

```ts twoslash [example.ts]
import { Module, Transport } from 'mppx'

const result = Module.method({
  param1: 'value1',
  transport: Transport.mcp(),
})
```

## Return Type

```ts
type ReturnType = {
  // describe the return type
}
```

## Parameters

### paramName

- **Type:** `TypeName`

Description of what this parameter does.

### optionalParam (optional)

- **Type:** `TypeName`

Description of the optional parameter.
````

### Example: Fetch.from

````mdx
# `Fetch.from`

Creates a fetch wrapper that automatically handles 402 Payment Required responses.

## Usage

::::code-group

```ts twoslash [example.ts]
import { Fetch, tempo } from 'mppx/client'
import { privateKeyToAccount } from 'viem/accounts'

const fetch = Fetch.from({
  methods: [tempo({ account: privateKeyToAccount('0x...') })],
})

const res = await fetch('https://api.example.com/resource')
// @log: Response { status: 200, ... }
```

::::

## Return Type

```ts
type ReturnType = (
  input: RequestInfo | URL,
  init?: RequestInit & { context?: AnyContextFor<methods> }
) => Promise<Response>
```

## Parameters

### methods

- **Type:** `readonly Method.AnyClient[]`

Array of payment methods to use for handling 402 responses.

### fetch (optional)

- **Type:** `typeof globalThis.fetch`

Custom fetch function to wrap. Defaults to `globalThis.fetch`.
````

## Writing style

Follow [Stripe's documentation style](https://stripe.com/docs). Key rules:

**Voice**: Active, present tense, second person ("you"). Use contractions.
- ✅ "The server returns a challenge"
- ❌ "A challenge will be returned by the server"

**Be concise**: Cut filler words (just, simply, easily, obviously). Don't claim things are "easy" or "fast."

**Formatting**:
- Sentence case for headings (not Title Case)
- Bold for UI elements and list labels
- Code font for parameters, commands, status codes, object names
- Em dashes with no spaces: "payments immediately—you don't need to"
- When discussing command names like `tempo wallet` or HTTP status code specifics like `402` you should always use code blocks ``

**MPP core concepts as proper nouns**: Capitalize Challenge, Credential, and Receipt when referring to these as MPP protocol concepts or SDK types. For example: "Parse a Challenge", "Verify a Credential", "Return a Receipt". These are proper nouns within the MPP domain.

**Terminology**: Use "stablecoins" instead of "crypto" when referring to on-chain payment methods. MPP uses stablecoins (OUSD, USDC.e) on Tempo—not generic cryptocurrency. Use OUSD in single-currency Tempo examples and setup. Prefer the SDK's OUSD-first defaults when showing fallback offers. Preserve actual provider defaults and chain-specific token requirements. Always use "USDC.e" (not "USDC") when referring to the bridged USDC token on Tempo. The only exception is when referring to Circle's USDC stablecoin in general (not Tempo-specific) contexts.

**`mppx`**: Always write the SDK and package name as lowercase `mppx`, including in prose and headings.

**Session funds terminology**: Never use "escrow" in prose. Use "reserve" for the noun and "reserve" or "lock up" for the verb, depending on context. Only use `escrow` when documenting an actual code identifier, parameter, or contract name that contains that word.

**Avoid**:
- Latin abbreviations (use "for example" not "e.g.")
- Future tense ("will") and conditional ("should")
- "Once" to mean "after"
- Exclamation points, humor, rhetorical questions
- The word "crypto"—use "stablecoins" instead
- "AI coding agent"—say "coding agent" instead (the "AI" is redundant)

**Structure**: Never skip heading levels. Keep headings under 12 words. Use imperative mood for procedures.

**H1 with bracketed tagline**: This project uses Vocs-style H1 headings with a bracketed tagline for page subtitles. This is an intentional deviation from Stripe style:
```md
# Page Title [Short tagline describing the page]
```
The bracketed text renders as a subtitle in Vocs. Do not remove these taglines or convert them to intro paragraphs.

## OG and social card text

Every page has two frontmatter fields that appear in social previews (Slack, Twitter, iMessage):

- **`description`** — Meta description shown below the link. Keep under 160 characters.
- **`imageDescription`** — Text rendered on the OG image card. Keep under 80 characters.

Both fields should read like marketing copy, not engineering docs:

- **Lead with the benefit or outcome**, not the mechanism
- **Use active voice and present tense**
- **Avoid jargon**: no "cryptographic", "off-chain", "state channels", "zero-copy parsing", "control flow", "x-payment-info extensions"
- **Don't start with "How" or "The"**—lead with an action or value prop
- **Don't restate the page title**—add context the title doesn't provide

**Examples:**
- Good: `imageDescription: "Charge for your API in a few lines of code"`
- Bad: `imageDescription: "Charge for access to protected API resources using challenges, credentials, and receipts"`
- Good: `imageDescription: "Connect your agent to paid APIs"`
- Bad: `imageDescription: "Connect your AI agent to MPP-enabled services and handle payments automatically"`

## Badges in tables

Use `<Badge variant="...">` in tables to indicate status or maturity. Import from `vocs`.

| Variant | Use For | Example |
|---------|---------|---------|
| `success` | Production-ready, stable, success states | `<Badge variant="success">Stable</Badge>` |
| `info` | Beta, preview, standard/recommended | `<Badge variant="info">Beta</Badge>` |
| `warning` | Coming soon, deprecated, caution states | `<Badge variant="warning">Coming Soon</Badge>` |
| `danger` | Error states, 4xx/5xx codes | `<Badge variant="danger">402</Badge>` |
| `note` | Custom/advanced options | `<Badge variant="note">Custom</Badge>` |
| `gray` | Neutral metadata | `<Badge variant="gray">any time</Badge>` |

## MPP

Conventions every MPP repository shares, pulled together from their AGENTS.md files. Synced from [`agents/shared.md`](https://github.com/tempoxyz/mpp-tools/blob/main/agents/shared.md) in tempoxyz/mpp-tools: edit it there. ### This file

- Keep it to `# <repository>` and a short paragraph, then `## Commands`, `## Layout`, `## Conventions`, then only the sections this repository needs, then this section.
- Write rules an agent can act on: commands, paths, constraints. Leave out background, history and anything the code, specs or README already say.
- When you learn a convention the hard way, add it to the section it belongs to in the same pull request.

### Code

- Make the smallest change that does the job and follow the surrounding code. Start concrete; extract an abstraction only once several real uses share it.
- Keep the public API narrow. Add rather than remove or rename, and mark what you replace as deprecated before deleting it.
- Document every exported item (JSDoc, rustdoc, docstrings, Go doc comments). Comments say why, not what.
- Match mppx, the reference SDK: its names (Challenge, Credential, Receipt, Method), defaults, errors and behavior, unless the language forces otherwise; say why when it does.
- The IETF drafts in tempoxyz/mpp-specs (paymentauth.org) are the source of truth for the protocol, and mppx settles what they leave open. Link them instead of restating them.
- Add no dependency without a reason the pull request states. Prefer the standard library and what the repository already uses.
- Never log or commit keys, credentials, signatures, authorization headers or raw upstream errors.
- Tempo chain IDs: mainnet `4217`, Moderato testnet `42431`. Never `98865`.

### Tooling

Use each language's standard toolchain, run through the commands in `## Commands`, and keep it clean with warnings as errors:

- TypeScript: pnpm, strict `tsc`, ESM with `.js` relative imports, the repository's configured formatter and linter, Vitest.
- Python: uv, ruff (format and lint), a strict type checker (pyright or ty), pytest or unittest.
- Rust: cargo, `cargo fmt`, `cargo clippy -D warnings`, `cargo test`.
- Go: `gofmt`, `go vet`, golangci-lint, `go test -race`.
- Swift: SwiftPM, `swift test -Xswiftc -warnings-as-errors`.
- Run the checks that cover your change before opening a pull request, and add tests for behavior that matters, next to the existing ones.
- Pin GitHub Actions by full commit SHA. Workflows start with `tempoxyz/gh-actions/actions/secure-runner` and get write tokens from GitHub STS policies in `.github/sts/`, never stored secrets.

### Changes

- Commits and pull request titles use Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`, optionally scoped.
- Never edit `CHANGELOG.md` by hand. Record a release note the way `## Conventions` says (changeset, `.changelog/` fragment, or none when a workflow writes it), in the past tense.
- Before 1.0, bump `patch` for everything except a breaking public API change, which is `minor`.
- Don't edit README files unless asked.
- Never force-push.

### Docs and prose

- Active voice, present tense, second person. Sentence-case headings. No filler (just, simply, easily) and no Latin abbreviations.
- Capitalize Challenge, Credential and Receipt as MPP concepts. Say stablecoins, not crypto, and USDC.e for bridged USDC on Tempo. Write `mppx` in lowercase.
