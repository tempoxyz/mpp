# Refunds [Return funds to clients]

## Overview

MPP does not define a dedicated refund protocol. How refunds work depends on the payment flow your service uses.

## Charge flow

In the charge flow, funds transfer to the server immediately when the client pays. Refunds are **out-of-protocol**—the server sends funds back to the client's address directly.

<MermaidDiagram chart={`sequenceDiagram
    participant Client
    participant Server
    Client->>Server: Request + Credential
    Note over Server: Funds transfer
    Server-->>Client: 200 OK + Receipt
    Note over Server: Refund triggered
    Server->>Client: Direct transfer back
`} />

For payments with an authenticated payer, record the verified payer address and return funds with a standard on-chain transfer. `source` is optional and may be a DID rather than an address; parsing it alone doesn't authenticate the payer.

Private [Zone payments](/guides/private-payments) omit both Credential `source` and Receipt `payer`. Don't infer a refund destination from their settlement transaction or an arbitrary client-supplied `source`. Use a separate authenticated refund policy and reconcile the original withdrawal before transferring funds.

### Implementation

For a charge with a verified payer address, refund to the address recorded during payment verification:

```ts twoslash [server.ts]
// @noEmit
declare const payment: { payer: string }
declare function sendTransfer(params: { amount: string; to: string }): Promise<void>
// ---cut---
async function refundCharge(payment: { payer: string }, amount: string) {
  await sendTransfer({ amount, to: payment.payer })
}
```

Refund decisions are up to your service. Common triggers include failed processing, service errors, or customer support requests.

## Session flow

In the v2 session flow, funds are reserved in a Tempo channel but not immediately claimed. If the server never claims the reserved funds, they return to the client after the session expires or closes.

This gives sessions a **built-in refund mechanism**—unclaimed funds are refunded by default.

<MermaidDiagram chart={`sequenceDiagram
    participant Client
    participant Server
    participant Tempo
    Client->>Tempo: Deposit tokens
    Tempo-->>Client: Channel created
    Client->>Server: Open Credential
    Server-->>Client: 200 OK (session established)
    loop Per request
        Client->>Server: Request + voucher
        Server-->>Client: 200 OK + Receipt
    end
    Note over Server: Close channel with last voucher
    Server->>Tempo: close(channelId, voucher)
    Note over Tempo: Settle claimed amount to server
    Tempo-->>Client: Refund unclaimed deposit
`} />

| Scenario | Outcome |
|----------|---------|
| Server claims funds | Payment completes, no refund |
| Server never claims | Funds return to client after session expiry |
| Server claims partial amount | Remaining funds return to client |

### Credit undelivered content

Use [`tempo.session.credit`](/sdk/typescript/server/Method.tempo.session#temposessioncredit) to reduce accepted spend that hasn't settled or become unavoidably settleable. Supply a stable `idempotencyKey`; retry an `unknown` outcome with that same key and terms before sending an external refund. A declined credit leaves spend unchanged. Preserve the key for every retry within its retention window (24 hours by default).

For managed SSE delivery failures, opt into [automatic prepaid credits](/sdk/typescript/server/Method.tempo.session#automatic-prepaid-credits) instead of running a second automatic refund handler. Persist `onRefundRequired` jobs and reconcile uncertain writes; only a non-null `externalRefundAmount` identifies captured funds safe to refund externally. Client cancellation and delivered content aren't automatically refunded.

### Refunding via channel close

To refund a session, close the channel with the last accepted voucher. Any unclaimed deposit returns to the client automatically.

## Best practices

- **Track the original payment**—Record the Challenge ID, settlement reference, and verified payer when available. Zone payments use a withdrawal `senderTag`, not a public payer identity.
- **Authenticate the refund destination**—Use the recorded, verified payer address for ordinary charges. Private payments need a separate authenticated policy; never trust an unverified refund address.
- **Treat refunds as a feedback mechanism** — Like traditional payment systems, refunds avoid costly disputes. Handle them promptly through your service's support process.
- **Log refund transactions** — Keep a record of the original payment and the refund transaction for reconciliation.
