# Accept usage-based payments [Bill per request or per token with sessions]

Use `mppx` sessions on Tempo to charge for usage. A session opens a payment channel once, then pays for each request or streamed token with an off-chain voucher.

- **[Per request](#per-request)**: charge a fixed amount for each API call.
- **[Streaming](#streaming)**: charge per token as content streams over Server-Sent Events (SSE).

:::info
Unlike [one-time payments](/guides/one-time-payments), vouchers are **not bottlenecked by blockchain throughput**—they're processed in pure CPU-bound signature checks.
:::

#### Set up `Mppx` instance

Set up an `Mppx` instance with the current `tempo.session` method.

- `account` signs server-side session settlement and close transactions.
- `currencies: [address]` accepts only OUSD when configuring a Tempo factory. Per-route overrides use singular `currency`.
- `store` keeps v2 Session channel state; use a durable atomic store in production.

```ts [app/api/sessions/photo/route.ts]
import { Store } from 'mppx'
import { Mppx, tempo } from 'mppx/nextjs'
import { privateKeyToAccount } from 'viem/accounts'

const account = privateKeyToAccount('0x0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef')

const mppx = Mppx.create({
  methods: [
    tempo.session({
      account,
      chainId: 4217,
      currencies: ['0x20c0000000000000000000006a37DA5C996874BE'], // OUSD on Tempo
      store: Store.memory(),
    }),
  ],
})
```

### Per-request client setup

Set `maxDeposit` to bound the tokens reserved per channel. Automatic channel management doesn't require this option, but an unattended client needs a limit. Unspent funds return when the channel closes. This is not a total budget across replacement channels; use an [access-key spending limit](/guides/managing-agent-spend) for that.

For an API you don't control, also pin `currencies` and `expectedRecipients`, and set `maxAmount` with explicit `decimals` to cap each unit price. Use one channel store per HTTP origin. Set a trusted `origin` to recover unknown server snapshots; see [origin-bound recovery](/sdk/typescript/client/Method.tempo.session#origin-bound-recovery).

<Tabs stateKey="account-source">
<Tab title="Accounts SDK">

```ts [client.ts]
import { Mppx, tempo } from 'mppx/client'
import { Provider } from 'accounts'

const provider = Provider.create({ mpp: false }) // Avoid double 402 handling; mppx is configured below.
await provider.request({ method: 'wallet_connect' })

const mppx = Mppx.create({
  methods: [tempo({
    account: provider.getAccount({ signable: true }),
    getClient: provider.getClient,
    maxDeposit: '1', // Reserve up to 1 OUSD per channel
  })],
})

// Each fetch automatically manages the session lifecycle:
// 1st request: opens channel on-chain, sends initial voucher
// 2nd+ requests: sends off-chain vouchers (no on-chain tx)
const res = await fetch('http://localhost:3000/api/sessions/photo')
```

- **`maxDeposit: '1'`**: Caps reserved funds at 1 OUSD per channel. At $0.01/photo, 1 OUSD covers 100 requests.
- The client handles the full session lifecycle automatically: channel open, voucher signing, and retry after `402` responses.
- If the server sets `suggestedDeposit`, the client uses `min(suggestedDeposit, maxDeposit)`.

#### Close the channel

After you're done making requests, close the channel to settle on-chain and reclaim unspent deposit:

<Tabs stateKey="account-source">
<Tab title="Accounts SDK">

```ts twoslash [client.ts]
import { tempo } from 'mppx/client'
import { Provider } from 'accounts'

const provider = Provider.create({ mpp: false }) // Avoid double 402 handling; mppx is configured below.
await provider.request({ method: 'wallet_connect' })

const session = tempo.session.manager({
  account: provider.getAccount({ signable: true }),
  getClient: provider.getClient,
  maxDeposit: '1',
})

const res = await session.fetch('http://localhost:3000/api/sessions/photo')

// Settle on-chain and reclaim unspent deposit
const receipt = await session.close()
```

### Streaming client setup

Use `tempo.session.manager()` from `mppx/client` to create a session manager. Use one manager and channel store per API origin: its first HTTP or HTTPS request pins that origin, and later requests or redirected responses from other origins are rejected. The `.sse()` method connects to the SSE endpoint and handles voucher renewal automatically—if the server requests a new voucher mid-stream, the client signs and sends one without interrupting the stream.

<Tabs stateKey="account-source">
<Tab title="Accounts SDK">

```ts [client.ts]
import { tempo } from "mppx/client";
import { Provider } from "accounts";

const provider = Provider.create({ mpp: false }) // Avoid double 402 handling; mppx is configured below.
await provider.request({ method: "wallet_connect" })

const session = tempo.session.manager({
  account: provider.getAccount({ signable: true }),
  getClient: provider.getClient,
  maxDeposit: "1", // Reserve up to 1 OUSD per channel
});

// .sse() returns an async iterable of SSE data payloads
const stream = await session.sse("http://localhost:3000/api/sessions/poem");

for await (const word of stream) {
  process.stdout.write(word + " ");
}
```

- **`tempo.session.manager()`** — Creates a session manager that handles the full Sessions lifecycle.
- **`.sse()`** — Connects to an SSE endpoint. Automatically sends new vouchers when the server emits `payment-need-voucher` events.
- **`maxDeposit: '1'`** — Reserves up to 1 OUSD. At $0.001/word, this covers ~1,000 words before the channel needs a top-up.

### Prepaid requests and failed delivery

- With `sse: true` and `unitType: 'request'`, payment is charged before your handler runs—once per request, not per chunk. This includes plain POST responses; POSTs with a body or query carry content—don't return a blanket `204`.
- Enable `sse: { autoCreditPrepaid: true, onRefundRequired }` to credit undelivered prepaid items after managed SSE failures. Don't combine this with another automatic refund handler.
- Delivered content, manual charges, and client cancellation aren't automatically refunded. Handle plain-response refunds in your application.
- Persist recovery jobs in `onRefundRequired`. Retry uncertain credits with the same key, amount, and units before external refunds; transfer only a non-null `externalRefundAmount`.

See [automatic prepaid credits](/sdk/typescript/server/Method.tempo.session#automatic-prepaid-credits) for recovery rules and limits.

### Charge dynamic amounts

Pass a `bigint` in base units to charge a different amount for a specific event. An explicit amount reserves that amount for the next emitted event; calling `charge()` without an argument uses the route's configured tick cost.

```ts
return result.withReceipt(async function* (stream) {
  await stream.charge(2_000n)
  yield 'premium-result'
})
```

### WebSocket alternative

Use WebSocket for bidirectional streaming. Vouchers and content share one socket; channel opening, signing, and closing work the same way.

On the server, use [`mppx.session.serveWebSocket()`](/sdk/typescript/server/Ws.serve) to reuse the Session method's store and automatic settlement schedule. On the client, use [`session.ws()`](/sdk/typescript/client/Method.tempo.session-manager#with-websocket-streaming) instead of `session.sse()`.

Configure `settlementSchedule` on `tempo.session()` for SSE or WebSocket streams. `mppx` evaluates the schedule after each committed nonzero stream charge.

Run [`tempo.session.superviseCloses`](/sdk/typescript/server/Method.tempo.session#temposessionsupervisecloses) every minute (every 5 minutes is fine with few open channels) to answer close requests for idle channels. See [Close supervision](/payment-methods/tempo/session#close-supervision) for the recommended setup.

Retryable scheduled settlement failures keep charged content served and leave the charge due for a later settlement. Use [`onSessionSettlementFailure`](/sdk/typescript/server/Method.tempo.session#onsessionsettlementfailure-optional) to monitor failures. Confirmed settlements remain successful if only the channel-store checkpoint fails; reverts and configuration errors still fail the charge.
