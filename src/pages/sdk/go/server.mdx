# Server [Protect endpoints with payment requirements]

Create a Tempo method with `charge.New`, pass it to `server.New`, then use middleware or call `Charge` directly.

## Quick start

```go [server.go]
method, err := charge.New(charge.Config{
	Recipient: "0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266",
	RPCURL:    "https://rpc.tempo.xyz",
	Store:     tempo.NewMemoryStore(), // Development only.
})
if err != nil {
	log.Fatal(err)
}

payment, err := server.New(
	method,
	"api.example.com",
	"replace-with-at-least-32-bytes-of-secret",
)
if err != nil {
	log.Fatal(err)
}

handler := server.ChargeMiddleware(payment, server.ChargeParams{
	Amount:      "0.50",
	Description: "Paid content",
})(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
	credential := server.CredentialFromContext(r.Context())
	receipt := server.ReceiptFromContext(r.Context())
	_ = json.NewEncoder(w).Encode(map[string]any{
		"payer":     credential.Source,
		"reference": receipt.Reference,
	})
}))
```

The secret must contain at least 32 bytes. Keep it in a secret manager.

## Replay protection

Local verification requires a `tempo.Store`. Production replicas must share a persistent implementation with atomic `PutIfAbsent`, no replay-key eviction, and fail-closed errors. `tempo.NewMemoryStore()` loses protection on restart and is only for single-process development. Relay verification delegates replay protection to the relay.

## Existing `Authorization` headers

```go
payment, err := server.New(
	method,
	"api.example.com",
	secret,
	server.WithRequiresAuth(true),
)
```

Challenges then advertise `Payment-Authorization`.

## Direct flow

```go
result, err := payment.Charge(r.Context(), server.ChargeParams{
	Amount:        "0.50",
	Authorization: r.Header.Get("Authorization"),
})
if err != nil {
	return err
}
if result.IsChallenge() {
	server.WritePaymentResponse(w, nil, result.Challenges...)
	return nil
}
```

## Framework integrations

`ChargeMiddleware` works with `net/http` and Chi. Dedicated adapters are available for Echo, Fiber, and Gin. Read the verified Credential and Receipt with `CredentialFromContext` and `ReceiptFromContext`.

## `charge.Config`

| Field | Type | Description |
|---|---|---|
| `AllowedFeeTokens` | `[]string` | Fee tokens a local sponsor accepts |
| `ChainID` | `int64` | Tempo chain bound into Challenges |
| `Currencies` | `[]string` | Ordered accepted TIP-20 addresses |
| `Decimals` | `int` | Token decimals used for route amounts |
| `FeePayerPrivateKey` | `string` | Local sponsorship key |
| `FeePayerSigner` | `*temposigner.Signer` | Custom local sponsor signer |
| `FeePayerURL` | `string` | Remote co-signer URL |
| `Recipient` | `string` | Default payment recipient |
| `Relay` | `*charge.RelayConfig` | Delegated validation and settlement |
| `RPC` | `tempo.RPCClient` | Custom RPC client |
| `RPCURL` | `string` | Tempo RPC endpoint |
| `Store` | `tempo.Store` | Required replay store for local verification |
| `SupportedModes` | `[]tempo.ChargeMode` | Accepted pull or push modes |

## Route parameters

`server.ChargeParams` accepts `Amount` and optional `Authorization`, `ChainID`, `Currency`, `Description`, `Expires`, `ExternalID`, `FeePayer`, `FeePayerURL`, `Memo`, `Meta`, `Recipient`, `Splits`, and `SupportedModes` values.

For paid POST routes, pass the caller's stable idempotency key as `ExternalID` and keep an application-level idempotency record. `ExternalID` is Receipt metadata; it does not prevent duplicate side effects by itself.

## Fee sponsorship

Configure `FeePayerPrivateKey` or `FeePayerSigner` and enforce fee-token and spending policies. An external fee-payer service must validate the full transaction, authenticate callers, simulate execution, and enforce per-caller and aggregate budgets before signing.
