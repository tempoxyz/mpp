# `Method.tempo.charge` [One-time payments]

## Choose a signing account

<SigningAccountTabs />

Creates a Tempo charge payment method for client-side transaction and proof signing.

## Usage

<Tabs stateKey="account-source">
<Tab title="Accounts SDK">

```ts twoslash
import { Mppx, tempo } from 'mppx/client'
import { Provider } from 'accounts'

const provider = Provider.create({ mpp: false }) // Avoid double 402 handling; mppx is configured below.
await provider.request({ method: 'wallet_connect' })

Mppx.create({
  methods: [
    // [!code focus:start]
    tempo.charge({
      account: provider.getAccount({ signable: true }),
      allowedChainIds: [42431], // Tempo testnet (Moderato)
      getClient: provider.getClient,
    }),
    // [!code focus:end]
  ],
})

const response = await fetch('https://mpp.dev/api/ping/paid')
```

</Tab>

- Nonzero Challenges produce a `transaction` or `hash` payload according to `mode`, or `zone` for [Zone payments](#zone-optional). Zero-amount Challenges always produce `proof`, without a transaction.
- The transaction's `validBefore` covers fractional-second Challenge expiry. Sponsored pull charges need at least 15 seconds of validity, checked before signing and after asynchronous preparation. Push and zero-amount Challenges are exempt.
- Currency, chain, recipient, and amount policies apply during selection and before signing. Concurrent requests with the same Challenge and signer share one signing operation.

MACH-enabled Challenges use the canonical swapper to pay the requested stablecoin. If unavailable, the client uses configured `autoSwap` or pays stablecoins directly. MACH supports single-recipient charges on mainnet and Moderato; fees use a funded, supported stablecoin.

[`machineTokenDeployments`](/sdk/typescript/tempo.machineTokenDeployments) in `mppx/tempo` lists canonical token and swapper addresses.

If the account holds neither enough MACH nor the stablecoin, payment fails with an insufficient-balance error. On mainnet, point the user to the MACH onramp—see [When the buyer has no MACH](/payment-methods/tempo/charge#when-the-buyer-has-no-mach).

### Cap each payment

Set a currency allowlist and amount cap before paying an API you don't control.

```ts twoslash
import { tempo } from 'mppx/client'
import { privateKeyToAccount } from 'viem/accounts'

const method = tempo.charge({
  account: privateKeyToAccount('0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80'),
  allowedChainIds: [42431], // Tempo testnet (Moderato)
  // [!code hl:start]
  currencies: ['0x20c0000000000000000000006a37DA5C996874BE'], // OUSD on Tempo
  decimals: 6,
  maxAmount: '1.00',
  // [!code hl:end]
})
```

### allowedChainIds (optional)

- **Type:** `readonly number[]`

Allowed Tempo chain IDs; use `[4217]` for mainnet.

- One entry supplies an omitted `chainId`; multiple entries require a Challenge or resolved-client chain.
- An empty list rejects all chains.
- A conflicting resolved-client chain is rejected.

### autoSwap (optional)

- **Type:** `boolean | { fallback?: boolean; maxAmountIn?: bigint; slippage?: number; tokenIn?: Address[] }`

Swaps supported stablecoins through the Tempo DEX precompile to acquire only the missing balance. Quote and balance reads work with new access keys before on-chain authorization.

Pass `true` or configure tokens and `slippage` (`0`–`50` percent). The default budget assumes 1:1 token units plus slippage; set a positive `maxAmountIn` in input-token base units for non-parity pairs. Quotes above the budget are skipped.

### clientId (optional)

- **Type:** `string`

Client identifier used to derive the client fingerprint in attribution memos.

### currencies (optional)

- **Type:** `readonly Address[]`

Allowlist of TIP-20 currency addresses, compared without case sensitivity. An empty list rejects every offer. Required when you set `maxAmount` or `maxAtomicAmount`.

### decimals (optional)

- **Type:** `number`

Decimals shared by the allowed currencies. Required to parse `maxAmount` because a Challenge doesn't carry currency decimals.

### expectedChainId (optional)

- **Type:** `number`

Accepted chain, also used when the Challenge omits `chainId`. Other chains are rejected. Use `allowedChainIds` for an allowlist shared with `tempo.session`; when both are set, both must match.

### feeToken (optional)

- **Type:** `Address`

TIP-20 fee token for unsponsored charges. Set it when an access key's limit excludes the default fee token; override per request with `context.feeToken`.

```ts
import { tempo } from 'mppx/client'
import { privateKeyToAccount } from 'viem/accounts'

const method = tempo.charge({
  account: privateKeyToAccount('0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80'),
  feeToken: '0x20c0000000000000000000006a37DA5C996874BE', // OUSD on Tempo
})
```

### getClient (optional)

- **Type:** `(parameters: { chainId: number }) => MaybePromise<Client>`

Function that returns a viem client for the given chain ID.

### maxAmount (optional)

- **Type:** `string`

Maximum display-unit amount per charge, parsed with `decimals`. Requires `currencies` and `decimals`. Values that require rounding are rejected. The cap includes split payments and applies to each Credential, not cumulatively across retries.

### maxAtomicAmount (optional)

- **Type:** `string`

Maximum amount per charge in the currency's base units. Requires `currencies`. The cap includes split payments and applies to each Credential.


### mode (optional)

- **Type:** `'push' | 'pull'`
- **Default:** `'push'` for JSON-RPC accounts, `'pull'` for local accounts

Controls how non-zero charge transactions are submitted. Zero-amount Challenges ignore this option and always use a `proof` payload.

- `'push'`: the client broadcasts the transaction and sends the transaction hash to the server for verification.
- `'pull'`: the client signs the transaction and sends the serialized transaction to the server, which broadcasts it. This is required for server-side [fee sponsorship](/quickstart/server#fee-sponsorship).

### resolveAccount (optional)

- **Type:** `ResolveAccount`

Selects the account that signs this charge after the Challenge and chain are known.

### zone (optional)

- **Type:** `{ client: Client; settlementTimeoutMs?: number; zoneId?: number }`

Pays from a [Zone](https://docs.tempo.xyz/docs/zones) when the Challenge's `methodDetails.zones` accepts it, permits push, and has no splits. Withdraws to the recipient with a Challenge-bound memo, waits for Tempo settlement, then sends a `zone` Credential. Other Challenges use Tempo.

- `client`: viem client for the Zone chain, with the paying account and the Zone RPC authorization token.
- `settlementTimeoutMs`: finite, non-negative milliseconds to wait for settlement on Tempo. Defaults to `60_000`. The client throws `Errors.ZoneSettlementPendingError` when the wait ends; creating the Credential again for the same Challenge resumes it without withdrawing again.
- `zoneId`: Zone ID. Derived from `client.chain.id` when omitted. An explicit ID must match an encoded client-chain Zone ID.

- The Zone must settle on the Challenge's chain. Explicit `mode: 'pull'` disables this path.
- New withdrawals require more than `settlementTimeoutMs + 15_000` milliseconds of Challenge validity; otherwise payment uses Tempo. Pending waits stop at Challenge expiry.

- Concurrent attempts for the same full Challenge share one withdrawal.
- After a lost send response, the client checks the signed transaction's known hash on the Zone for up to 15 seconds. An unknown outcome blocks another withdrawal for that Challenge; reconcile on-chain before paying another Challenge.
- Pre-submission failures and confirmed reverts are safe to retry.
- Pending state is in memory and cleared after settlement. Retain and reuse the resulting Credential instead of paying again.

See [private payments](/guides/private-payments).
